A homelab earns its keep the day it replaces a subscription. Family photos that used to live in Google's cloud, on a plan that gets a little more expensive every year, now live on a drive I own outright. Documents that used to mean an hour digging through a shoebox now OCR themselves into something searchable without me lifting a finger. That's the whole case for a homelab: cheaper, more private, and more useful than whatever it replaced. Nothing runs here that doesn't clear that bar.

My homelab is great hardware fighting mediocre software, and the hardware mostly wins. The main node is an M2 Max MacBook Pro with 64 GB of RAM, wired into the router over USB ethernet, with a 16 TB drive plugged into the MacBook itself over USB. It's not a dedicated box either; this is the same machine I write code on, do client work on, and use for everything else day to day. The homelab is one more set of terminal windows and Docker containers running alongside whatever else is open. I'd put the hardware up against anything else Apple has ever sold. It's silent under full load, it idles under ten watts where rack gear budgets hundreds, the battery doubles as a UPS, and it was already paid for. The machine itself doesn't need to be a MacBook. A Mac mini or an old ThinkPad gathering dust in a closet does the same job; the only requirement is that it's already yours and doesn't need to be perfect.

The obvious homelab move is Proxmox, or TrueNAS, or Unraid. Wipe a machine, install a bare-metal hypervisor or NAS OS, run everything as VMs or LXC containers on top of a disk array. That doesn't fit here, and not because those tools are bad. Proxmox and ESXi have no official Apple Silicon support, and even on hardware where they'd run, installing one turns the machine into something dedicated to a rack, not a laptop I can close and carry around. TrueNAS and Unraid solve a problem this setup doesn't have; they're built around multiple drives in a redundant array, and there's exactly one external drive here, not a pool. Docker Compose runs on top of an OS I'm already using for everything else. That's the actual appeal: the homelab rides along on a daily machine instead of a machine built to be a homelab.

Standing between that hardware and a real server is one thing: [Docker Desktop](https://www.docker.com/products/docker-desktop/), which [runs every container inside a hidden Linux VM](https://docs.docker.com/desktop/features/networking/) instead of talking to the kernel directly. That single decision causes most of the friction described in this post. It hides real client IPs behind a NAT gateway. It broke DNS resolution for `host.docker.internal` in a routine engine update. It wedges hard enough to need a weekly scheduled restart. It hides named Docker volumes from the backup agent inside a disk image nothing else can see into. Every one of those traces back to Docker Desktop's design; the M2 Max underneath has nothing to do with any of it.

A Raspberry Pi and a free ARM VM in someone else's datacenter round out the fleet. Most of what follows is about making this hardware behave like a real server anyway.

## Network setup and the request path

Getting a domain to find the house at all starts with a static IP from the ISP, unusual for a residential connection and one less moving part to worry about. [DuckDNS](https://www.duckdns.org/) points every subdomain at that IP, `dashboard.<mydomain>.duckdns.org`, `photos.<mydomain>.duckdns.org`, and the rest, refreshed by a five-minute Homebrew agent as insurance against the one day the ISP decides otherwise. The same DuckDNS account issues the TLS certificate. Let's Encrypt validates ownership through a DNS challenge against DuckDNS's API instead of the usual HTTP challenge, so one wildcard certificate covers every subdomain without opening a single port to prove it.

About twenty-five containers run the usual self-hosting roster plus my own work. [Immich](https://immich.app/) handles photos, [paperless-ngx](https://github.com/paperless-ngx/paperless-ngx) handles documents, [Home Assistant](https://www.home-assistant.io/) runs the house, [Audiobookshelf](https://www.audiobookshelf.org/) serves audiobooks, [Stirling PDF](https://github.com/Stirling-Tools/Stirling-PDF) does PDF tooling, [Glance](https://github.com/glanceapp/glance) drives the dashboards, [Open WebUI](https://github.com/open-webui/open-webui) fronts a local LLM, and [SnapOtter](https://snapotter.com/) is the file-processing tool I develop and dogfood here. [Nginx Proxy Manager](https://nginxproxymanager.com/) terminates TLS. [Pi-hole](https://pi-hole.net/), on a Raspberry Pi plugged straight into the main router, filters DNS. [Tailscale](https://tailscale.com/) carries everything administrative, and the main router forwards exactly two ports. The house actually runs three routers, the main one plus one in each bedroom, all broadcasting the same network name so a phone roams the whole house without switching WiFi. Only the main one holds the public IP and does any forwarding; the other two just extend coverage.

The apartment's wired backbone is a hack on top of a builder's oversight. The builder ran actual Cat5e cable to every telephone point in the unit, the same cable real Ethernet needs, just wired and terminated for a phone line instead of a network. Rather than pay an electrician to fish new cable through the walls, I went jack by jack and converted each telephone port into a proper LAN port, riding the same cable that was already there. The apartment now has wired Ethernet in nearly every room, and not one new cable run through the walls made that happen.

An external request does not go straight to Docker. The reason is the most macOS-specific fact in this whole setup: Docker Desktop runs containers inside a VM and [NATs](https://www.cisco.com/site/us/en/learn/topics/networking/what-is-network-address-translation-nat.html) every forwarded connection, so by the time a request reaches a containerized proxy, every client on earth appears to come from the same gateway address. Tooling that reads those logs to decide who to ban learns nothing from them. A native nginx on the host owns ports 80 and 443 instead, logs real client addresses, and forwards into Docker, where NPM does TLS and routing. A service doesn't see a byte until it's passed through two proxies, and each layer covers something the other can't.

Docker's own defaults needed correcting twice more. Its address pool overlaps the same private ranges home routers use, so the daemon is pinned to `172.16.0.0/12` before it collides with the LAN. A Docker engine update quietly broke `host.docker.internal` resolution for nginx's resolver, so the proxy now targets the VM's gateway address directly. Neither fix appears in any tutorial. Both came out of debugging evenings.

## What it's actually for

All that plumbing exists to protect things that are almost boringly ordinary. Immich holds the family photo library and gets used by relatives abroad, which is the actual reason it stays public instead of hiding behind Tailscale like everything administrative. Getting years of photos out of Google's ecosystem and into it was its own project: a full Google Takeout export, then [immich-go](https://github.com/simulot/immich-go) to walk the archive and upload everything while keeping the original timestamps and album structure, the two things a naive drag-and-drop re-upload would have thrown away. paperless-ngx OCRs every scanned bill, form, and letter into something you can actually search, and "where did I put that visa paperwork from two years ago" stopped being a real question. Home Assistant runs the house itself. Four smoke and CO alarms feed into one automation that names the room, speaks a warning aloud on both phones, and keeps repeating every 30 seconds for up to ten minutes until someone hits silence or the air actually clears. The CCTV camera records 30-second motion clips with a 5-second lookback and prunes itself after 30 days. The air conditioners, fans, and balcony blinds take a schedule or a voice command instead of a remote somebody has to go find.

Most of the sensors behind all of that are cheap on purpose. The plugs and IR blasters are inexpensive Tuya hardware, a fraction of the cost of a name-brand equivalent, and they've held up fine. The smoke and CO alarms are the exception. The first round of cheap Tuya units weren't good enough for something safety-critical, so those got replaced with an SCDF-listed smoke and carbon monoxide detector, WiFi and mobile connected and interlinked between units, noticeably more expensive, and still Tuya underneath. Cheap where cheap is fine, certified where it isn't.

All of it talks to Home Assistant through [Tuya's own cloud integration](https://www.home-assistant.io/integrations/tuya/), which is also the officially documented path if you'd rather replicate this than reverse-engineer it from a blog post. Voice control skips Home Assistant entirely. The same devices are linked a second time, directly, through the [Smart Life app into Google Home](https://developer.tuya.com/en/docs/iot/googlehomeguide?id=K9j6yqpeqzzgp), because the Nabu Casa subscription that would bridge Home Assistant to Google runs about eight dollars a month forever, and exposing Home Assistant to the internet just so a speaker can hear it isn't worth the trade. The IR-controlled ACs need one more piece, a [HACS](https://hacs.xyz/) community integration called `tuya_smart_ir_ac`, since IR blasting isn't something core Home Assistant or Tuya's cloud API handles natively. One path automates the house, the other answers to "hey Google," and neither needs the other to work. Audiobookshelf plays audiobooks and podcasts to whichever phone is nearby. Open WebUI talks to a locally running Ollama, so asking a model a question never has to leave the apartment. SnapOtter, the file-processing tool I build for a living, runs here first, on my own files, catching most bugs before a customer does. I don't feature-creep any of it for its own sake. Every container on this box earns its place by doing something a person in this apartment actually needs done.

## Blocking traffic with CrowdSec and pf

[CrowdSec](https://www.crowdsec.net/) tails the native nginx logs with the nginx, base-http-scenarios, and http-cve collections, merges its findings with a community blocklist about fifteen thousand addresses deep, and publishes ban decisions on a localhost-only API. Enforcement happens at the kernel. A [pf](https://www.openbsd.org/faq/pf/) anchor holds one persistent table, and a rule drops matching traffic before any application sees it.

```
table <crowdsec_blocklist> persist
block drop in quick from <crowdsec_blocklist> to any
```

CrowdSec ships no pf bouncer for macOS, so mine is forty lines of shell on a root [launchd](https://support.apple.com/guide/terminal/script-management-with-launchd-apdc6c1077b-5d5d-4d35-9c19-60f2397b2369/mac) daemon. Every thirty seconds it pulls the decision list, writes it to a file, and runs `pfctl -T replace` to swap the table wholesale. Wholesale replacement is the reliable choice here. The table always equals the current decision list, there's no drift to reconcile, and a crashed cycle heals itself thirty seconds later. It usually holds a few hundred addresses that earned their place.

What this setup still can't see is the traffic that matters most. Native nginx only terminates port 80; port 443 is a raw TCP passthrough straight to NPM, so CrowdSec's log-based detection reads full request detail on HTTP and effectively nothing on HTTPS, which is most real traffic. Closing that gap means either terminating TLS at the native layer too or feeding CrowdSec from NPM's own logs instead, and as of this writing it's still open.

## The eight-day database outage

The reliability engineering exists because of one incident. The Immich [Postgres](https://www.postgresql.org/) data directory used to live on the 16 TB USB drive. The drive dropped for a moment in August, and the database corrupted. Nothing alerted, because the web app kept returning HTTP 200 while its database lay dead behind it, and the outage ran eight days before a human noticed the photos were gone.

Every fix since traces back to that lie. The database moved to the internal SSD, so a USB dropout now costs photo visibility and never data integrity. [Uptime Kuma](https://github.com/louislam/uptime-kuma) grew container-level monitors on a read-only Docker socket, because an HTTP check believes a service that answers, and a container check believes only a process that runs. And the drive itself got a watchdog with hands.

## Watchdogs and self-healing

Seven launchd jobs patrol the machine on tight loops, and the interesting ones remediate before they page. They all report through the same channel: a Telegram bot hit with a plain `curl` call and a shared credentials file, so a phone buzzes instead of an inbox nobody reads at 3 a.m.

The drive watchdog checks the 16 TB mount every sixty seconds. On a dropout it attempts three remounts a minute apart, restarts the three stacks that depend on the volume, verifies their health, and only then reports the outcome. It also refuses to restart containers while the drive is absent, because healing into a missing mount just manufactures a second incident.

The container watchdog carries the subtle trick. A Docker [`restart: always`](https://docs.docker.com/engine/containers/start-containers-automatically/) policy revives a stopped container but reuses its cached configuration, so if a bind mount vanished, the restart fails exactly where the crash did. The watchdog instead runs `docker compose up -d --force-recreate --no-deps`, which rebuilds the container object and re-evaluates every mount as if fresh. It also carries a flap guard: two heals per container per six hours, then one "flapping" alert and a deliberate stop. A watchdog without a give-up threshold is an outage amplifier with good intentions.

The bluntest job is a scheduled Sunday 04:30 restart of Docker Desktop itself. Five wedges in three weeks, every one on a VM that had been up for weeks, is an empirical argument that macOS Docker uptime is a failure mode, so uptime now caps at seven days by appointment. macOS had its own time bomb too. The OS shipped with automatic update installs enabled, meaning it could reboot itself into a [FileVault](https://support.apple.com/guide/mac-help/encrypt-your-mac-data-with-filevault-mh11785/mac) unlock screen at 3 a.m. and take the whole lab down until a human typed a password. That setting is off now, FileVault stays on deliberately, and the rare unattended reboot is a risk the external watchdogs carry.

The Raspberry Pi covers the failure none of the Mac's own watchdogs can ever report: the Mac going fully dark. It pings the Mac on a cron loop and alerts if the whole machine goes silent, and the Mac pings back every five minutes, watching the Pi the same way. Each one notices what the other can't see in itself.

The off-site ARM VM is the gap that doesn't close yet. It exists, it's reachable over Tailscale, and a [dead man's switch](https://healthchecks.io/about/) script already runs on the Mac every five minutes waiting for somewhere to ping, but nothing points it anywhere yet. A full apartment power or ISP outage today takes the Pi's alerting down with it, and nothing off-site would notice. Wiring that switch to the ARM VM is next.

## Backups that have actually been restored

The nightly job at 03:00 dumps the Immich database with [`pg_dumpall`](https://www.postgresql.org/docs/current/app-pg-dumpall.html), tars ten named Docker volumes through throwaway [Alpine](https://www.alpinelinux.org/) containers, and snapshots the SQLite databases with [`sqlite3 .backup`](https://www.sqlite.org/backup.html). Copying a live database file is how you back up corruption, so the snapshot method matters as much as the schedule. Every artifact gets verified on the spot with `gzip -t` and `tar -tzf`, and the job aborts loudly if free disk drops below its floor.

Secrets and the small databases get encrypted with [age](https://github.com/FiloSottile/age) before they leave the machine, then pushed to a private git vault using a trick I like: each push is an orphan commit force-pushed over the last, so the repo carries tonight's backup and no history, and stays small forever. Oversized artifacts get slimmed to fit, including the uptime monitor's database, which drops from hundreds of megabytes to a few once the heartbeat history tables are purged. The age key lives in the password manager. That's the recovery path if the laptop itself is gone.

The vault and the nightly dump don't cover the 16 TB of photos and documents that make the lab worth protecting in the first place. That's [Backblaze](https://www.backblaze.com/)'s job, and it's the reason the setup has an off-site copy at all, the part of the [3-2-1 backup rule](https://www.backblaze.com/blog/the-3-2-1-backup-strategy/) that's easiest to skip and the one that would have mattered most if the apartment itself were the thing that failed. Its Personal Backup client runs continuously in the background and covers both the internal SSD and the external drive, but it only sees ordinary files. Docker Desktop's VM disk image is opaque to it, so a named Docker volume living inside that image never shows up in a Backblaze scan. That's exactly why the nightly script tars each one out to a plain file first. The Immich database dump is Backblaze's alone to protect; at 772 MB it's too big for the git vault's 90 MB ceiling. Default version history is 30 days, longer than the eight days the corrupted database sat unnoticed but not by a margin I trust, so it's extended to a year for about two dollars a month. Restoring multiple terabytes over residential fiber takes days. Backblaze's mail-in restore option exists for that reason alone.

Two safeguards make the pipeline trustworthy. The job pushes a heartbeat to the uptime monitor on success, and silence for twenty-six hours raises an alert, so a quietly broken backup gets one day to exist before anyone finds out. A restore-test script also loads the newest dump into a scratch container and asserts the photo count is nonzero, using the same Postgres image as production, because Immich's vector extensions mean a generic Postgres would pass the test and fail the real restore.

## The lab rebuilds from a git clone, mostly

Every `docker-compose.yml` in this repo is the actual infrastructure, not documentation describing it. `docker compose up -d` per service is the whole deployment mechanism, tracked in git, with no drift between what's written down and what's running. One script, `bootstrap.sh`, walks a fresh machine through the rest: checks Docker is running and the drive is mounted, places the `.env` files from the decrypted secrets bundle, brings every service up in dependency order, restores each stateful volume from the newest backup tar if it comes up empty, and installs the launchd watchdogs. It's idempotent, so running it twice does nothing the first run didn't already do.

Not everything fits in a compose file. Nginx Proxy Manager, Uptime Kuma, and Home Assistant are GUI-first tools that keep their real configuration in a database or a data directory, and forcing them into full declarative config would mean fighting the tools forever for a small slice of the benefit. Home Assistant gets the honest version of infrastructure as code, its config directory git-tracked directly. NPM and Kuma get the pragmatic version: their databases are dumped and encrypted every night as part of the same backup pipeline described above. Restorable isn't the same as declarative, but the difference matters less than it sounds like it should on the day the Mac is actually gone.

The full test is written down as a runbook, not just assumed. Clone the repo, pull the secrets bundle and the age key from the password manager, run `bootstrap.sh`, restore the Immich database from the latest dump, and the target is under two hours from a dead machine to a working one. That full drill hasn't actually happened yet. What has happened, repeatedly, is restoring one service, rebuilding one container, recovering one database in isolation. Each of those builds more confidence in the seams than an untested plan that only looks clean on paper.

## The kiosk dashboard

An old phone mounted under the monitor runs a kiosk dashboard served by a container, which raises an obvious question: what does the dashboard show when Docker itself dies? A small stats agent runs on the host, outside Docker, and the kiosk page detects the dashboard going quiet, covers the stale frame with a plain "Docker is down" banner, and keeps rendering live CPU and memory from the agent. Observability that dies with the thing it observes is decoration.

## Day-to-day use

For the people actually using these services, almost none of the engineering above is visible. Family abroad opens a plain HTTPS link to see new photos; nobody types a Tailscale key or remembers a port number. The kiosk phone needs no attention to stay current. New tiles and layout changes reach it through a 60-second data refresh, and changes to the dashboard itself self-propagate to the wrapper within 30 minutes, so it's never more than half an hour behind reality. A second dashboard, [Homepage](https://github.com/gethomepage/homepage), just lists links and live container status for every service, so "which port was Stirling PDF on again" stopped being a question I ask myself. Audiobookshelf and Home Assistant both have real mobile apps, and most days nobody opens a browser at all.

A few things sit between fully public and fully private. The kiosk dashboard is reachable from anywhere but gated by an HTTP basic-auth access list in NPM, so it degrades to a login prompt instead of joining the fully open group. Nothing that counts as a secret, API tokens, database passwords, the age key, ever gets near a commit either: every `.env` and `.db.env` file is gitignored, and the ones that do leave the machine leave encrypted, in the vault described earlier.

The public and private split is real, and bigger on the public side than I'd have guessed before actually checking it. Nine services are live on public subdomains right now: Immich, SnapOtter, Home Assistant, paperless-ngx, Stirling PDF, DrawIO, Audiobookshelf, Open WebUI, and the kiosk dashboard. NPM's own admin panel, Uptime Kuma, [Dozzle](https://github.com/amir20/dozzle), and [FileBrowser](https://github.com/filebrowser/filebrowser) never got a public proxy host at all; they're LAN and Tailscale only. A few of them do have leftover proxy-host rows from an earlier, more permissive draft of this setup. Checked against NPM's live config rather than the raw database, those rows turn out to be soft-deleted and serve nothing, confirmed by hitting them directly and getting no response at all. Stale rows in a database aren't an open door, but they're worth deleting properly instead of leaving them half-buried.

## What the lab taught

1. Docker on macOS launders every attacker into the gateway IP, so the first hop must live outside Docker. The native-nginx-plus-pf sandwich exists because of that one NAT fact.
2. [HTTP 200 is not health](https://sre.google/sre-book/monitoring-distributed-systems/). Immich answered cheerfully for eight days while its database was dead; monitor the process and the query path, and treat a green HTTP check as the weakest witness.
3. `restart: always` heals crashes and preserves the cause. Recreating the container re-evaluates mounts and config; restarting it replays them.
4. A watchdog needs a give-up threshold. Two heals per six hours, then alert and stand down, or the healer becomes the incident.
5. A backup without a heartbeat fails silently, and a backup without a restore test is a rumor with a filename. Test restores against the production image, because extensions make a generic database a false witness.
6. Cap uptime when the evidence says so. Five Docker wedges in three weeks bought a standing Sunday restart, and the wedges stopped.
7. A dead server cannot email you. Every monitor needs one watcher outside its own failure domain, which is why the Raspberry Pi and the Mac watch each other. The off-site VM is meant to be the third watcher, a whole-outage dead man's switch; that part is still unwired.
