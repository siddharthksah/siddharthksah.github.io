The point of my homelab is replacing subscriptions. Family photos that used to live in a cloud photo service now live on a drive I own. Documents that used to mean an hour digging through a shoebox now OCR themselves into something searchable. Everything running here is cheaper, more private, or more useful than what it replaced, and usually all three.

The main node is an M2 Max MacBook Pro with 64 GB of RAM, wired into the router over USB ethernet, with a 16 TB drive plugged into the MacBook over USB. It isn't a dedicated box. This is the same machine I write code on, do client work on, and use for everything else day to day. The homelab is one more set of terminal windows and Docker containers running alongside whatever else is open. The hardware suits the job. It's silent under full load, it idles under ten watts where rack gear budgets hundreds, the battery doubles as a UPS, and it was already paid for. It doesn't need to be a MacBook. A Mac mini or an old ThinkPad in a closet does the same job. The only requirement is that it's already yours.

The usual homelab move is Proxmox, or TrueNAS, or Unraid. Wipe a machine, install a bare-metal hypervisor or NAS OS, run everything as VMs or LXC containers on top of a disk array. Those don't fit this setup. Proxmox and ESXi have no official Apple Silicon support, and even on hardware where they'd run, installing one turns the machine into something dedicated to a rack. TrueNAS and Unraid solve a problem this setup doesn't have. They're built around multiple drives in a redundant array, and there's exactly one external drive here. Docker Compose runs on top of an OS I'm already using for everything else, and that's the appeal. The homelab rides along on a daily machine.

The main source of friction is [Docker Desktop](https://www.docker.com/products/docker-desktop/), which [runs every container inside a hidden Linux VM](https://docs.docker.com/desktop/features/networking/) and never talks to the kernel directly. That one design decision causes most of the problems in this post. It hides real client IPs behind a NAT gateway. It broke DNS resolution for `host.docker.internal` in a routine engine update. It wedges often enough to need a weekly scheduled restart. It hides named Docker volumes from the backup agent inside a disk image nothing else can see into. All of those come from Docker Desktop, none from the hardware.

A Raspberry Pi and a free ARM VM in someone else's datacenter round out the fleet. Most of what follows is about making this hardware behave like a real server anyway, with enough of the mechanics that you could rebuild it.

## Network setup and the request path

First, the domain has to resolve to the house. The DNS records point at the home connection's public address, and a small launchd agent on the Mac re-checks that address every five minutes and updates the records through the DNS provider's API if it changes. Certificates come from Let's Encrypt through the ACME DNS-01 challenge. The client asks for a wildcard certificate, Let's Encrypt hands back a token, the client writes the token into a `_acme-challenge` TXT record through the same API, and Let's Encrypt reads the record to prove control of the domain. That's the mechanism that lets one wildcard certificate cover every subdomain without opening a port to prove anything, and it renews itself at sixty days against a ninety-day validity.

About twenty-five containers run the usual self-hosting roster plus my own work. [Immich](https://immich.app/) handles photos, [paperless-ngx](https://github.com/paperless-ngx/paperless-ngx) handles documents, [Home Assistant](https://www.home-assistant.io/) runs the house, [Audiobookshelf](https://www.audiobookshelf.org/) serves audiobooks, [Stirling PDF](https://github.com/Stirling-Tools/Stirling-PDF) does PDF tooling, [Glance](https://github.com/glanceapp/glance) drives the dashboards, [Open WebUI](https://github.com/open-webui/open-webui) fronts a local LLM, and [SnapOtter](https://snapotter.com/) is the file-processing tool I develop and run here on my own files. [Nginx Proxy Manager](https://nginxproxymanager.com/) terminates TLS. [Pi-hole](https://pi-hole.net/), on the Raspberry Pi, filters DNS for the LAN. [Tailscale](https://tailscale.com/) carries everything administrative. It's WireGuard underneath, each device has its own key, and an access list grants the admin tools to my own devices only, so they never need a public hostname at all. A few services are reachable from outside so family can use them, and the router forwards only what the reverse proxy needs.

The apartment's wired network came from a builder's oversight. The builder ran Cat5e cable to every telephone point in the unit, the same cable Ethernet needs, just terminated for a phone line. I went jack by jack and converted each telephone port into a LAN port on the same cable. The apartment now has wired Ethernet in nearly every room without a single new cable run through the walls.

An external request doesn't go straight to Docker. This is the most macOS-specific part of the setup. Docker Desktop runs containers inside a VM and [NATs](https://www.cisco.com/site/us/en/learn/topics/networking/what-is-network-address-translation-nat.html) every forwarded connection, so by the time a request reaches a containerized proxy, every client on earth appears to come from the same gateway address. Tooling that reads those logs to decide who to ban gets nothing useful. So a native nginx on the host owns ports 80 and 443, logs real client addresses, and forwards into Docker, where NPM does TLS and routing. Every request passes through two proxies, and each covers something the other can't.

Docker's own defaults needed fixing twice more. Its default address pool overlaps the private ranges home routers use, so the daemon is pinned to a range that doesn't collide with the LAN, set through the `default-address-pools` key in the daemon config. A Docker engine update quietly broke `host.docker.internal` resolution for nginx's resolver, so the proxy now targets the VM's gateway address directly. I didn't find either fix in a tutorial.

## What runs on it

The services themselves are ordinary. Immich holds the family photo library, and relatives abroad use it, which is the reason anything faces the internet at all. Moving years of photos off the old cloud service was its own project: a full account export, then [immich-go](https://github.com/simulot/immich-go) to walk the archive and upload everything while keeping the original timestamps and album structure, the two things a drag-and-drop re-upload would have thrown away. The export splits metadata into sidecar JSON files next to the images, and immich-go's job is mostly matching each sidecar to its photo and writing the capture time back into the upload, since the file's own modification time is the export date. paperless-ngx OCRs every scanned bill, form, and letter into something searchable, and "where did I put that visa paperwork from two years ago" stopped being a question. Home Assistant runs the house. Four smoke and CO alarms feed into one automation that names the room, speaks a warning aloud on both phones, and keeps repeating every 30 seconds for up to ten minutes until someone hits silence or the air clears. The camera records 30-second motion clips with a 5-second lookback and prunes itself after 30 days. The air conditioners, fans, and balcony blinds take a schedule or a voice command.

Most of the sensors behind all of that are cheap. The plugs and IR blasters are inexpensive Tuya hardware, a fraction of the cost of a name-brand equivalent, and they've held up fine. The smoke and CO alarms are the exception. The first round of cheap Tuya units weren't good enough for something safety-critical, so those got replaced with a certified smoke and carbon monoxide detector, WiFi and mobile connected and interlinked between units, noticeably more expensive, and still Tuya underneath. I spent money on the safety-critical parts and went cheap on the rest.

All of it talks to Home Assistant through [Tuya's own cloud integration](https://www.home-assistant.io/integrations/tuya/), which is also the officially documented path if you want to replicate this. Voice control skips Home Assistant entirely. The same devices are linked a second time, directly, through the [Smart Life app into the voice assistant](https://developer.tuya.com/en/docs/iot/googlehomeguide?id=K9j6yqpeqzzgp), because the Nabu Casa subscription that would bridge Home Assistant to it costs about eight dollars a month forever, and exposing Home Assistant to the internet just so a speaker can hear it isn't worth it. The IR-controlled ACs need one more piece, a [HACS](https://hacs.xyz/) community integration called `tuya_smart_ir_ac`, since neither core Home Assistant nor Tuya's cloud API handles IR blasting natively. One path automates the house and the other answers to voice, and neither needs the other. Audiobookshelf plays audiobooks and podcasts to whichever phone is nearby. Open WebUI talks to a locally running Ollama, so asking a model a question never leaves the apartment. SnapOtter, the file-processing tool I build for a living, runs here first, on my own files, and catches most bugs before a customer does. Everything on the box is something someone in the apartment uses.

## Blocking traffic with CrowdSec and pf

[CrowdSec](https://www.crowdsec.net/) tails the native nginx logs with the nginx, base-http-scenarios, and http-cve collections, merges its findings with a community blocklist about fifteen thousand addresses deep, and publishes ban decisions on a localhost-only API. Enforcement happens at the kernel. A [pf](https://www.openbsd.org/faq/pf/) anchor holds one persistent table, and a rule drops matching traffic before any application sees it.

```
table <crowdsec_blocklist> persist
block drop in quick from <crowdsec_blocklist> to any
```

The anchor loads from its own file, so the rest of pf's ruleset stays untouched, and `quick` means pf stops evaluating at the first match, so a banned address never reaches the pass rules further down. CrowdSec ships no pf bouncer for macOS, so mine is forty lines of shell on a root [launchd](https://support.apple.com/guide/terminal/script-management-with-launchd-apdc6c1077b-5d5d-4d35-9c19-60f2397b2369/mac) daemon. Every thirty seconds it pulls the decision list, writes it to a file, and runs `pfctl -a crowdsec -t crowdsec_blocklist -T replace -f` on that file to swap the table wholesale. Wholesale replacement is the reliable option. The table always equals the current decision list, there's no drift to reconcile, and a crashed cycle heals itself thirty seconds later. Each cycle writes the decision count to a state file, so a dead bouncer looks different from an empty list. The table usually holds a few hundred addresses.

The gap is HTTPS. Native nginx only terminates port 80. Port 443 is a raw TCP passthrough straight to NPM through nginx's `stream` module, so CrowdSec's log-based detection reads full request detail on HTTP and almost nothing on HTTPS, which is most real traffic. The fix I'm partway through is the PROXY protocol. The native layer prefixes each forwarded connection with a one-line header carrying the real client address, and NPM's nginx is configured to read that header and log the address it finds there. Then NPM's own access log carries real addresses, CrowdSec can tail that log, and the native layer stays a dumb TCP forwarder. As of this writing the config is written and the cutover isn't done.

## The eight-day database outage

Most of the reliability work exists because of one incident. The Immich [Postgres](https://www.postgresql.org/) data directory used to live on the 16 TB USB drive. The drive dropped for a moment in August, and the database corrupted. Nothing alerted, because the web app kept returning HTTP 200 while its database was dead behind it, and the outage ran eight days before a human noticed the photos were gone.

Here's what killed the database. Postgres survives a clean power loss because it writes every change to a log before it touches the data files, and replays the log on restart. A USB drive that vanishes mid-write is different: the write fails partway, Postgres treats a failed log write as fatal, and when the drive comes back the log and the data files disagree in a way no replay can fix. The internal SSD doesn't drop.

Every fix since came out of that. The database moved to the internal SSD, so a USB dropout now costs photo visibility and never data integrity. [Uptime Kuma](https://github.com/louislam/uptime-kuma) grew container-level monitors on a read-only Docker socket, because an HTTP check only tells you the web server is answering. And the drive got a watchdog that can remount it.

## Watchdogs and self-healing

Seven launchd jobs run on short intervals, and the interesting ones fix things before they alert. They all report through the same channel: a Telegram bot hit with a plain `curl` call and a shared credentials file, so alerts arrive on a phone. Each is a plist with `StartInterval` for the loop and `KeepAlive` off, so a crashed watchdog doesn't respawn in a loop of its own.

The drive watchdog checks the 16 TB mount every sixty seconds. On a dropout it attempts three remounts a minute apart, restarts the three stacks that depend on the volume, verifies their health, and only then reports the outcome. It also refuses to restart containers while the drive is absent, because starting containers against a missing mount causes a second problem.

The container watchdog does one non-obvious thing. A Docker [`restart: always`](https://docs.docker.com/engine/containers/start-containers-automatically/) policy revives a stopped container but reuses its cached configuration, so if a bind mount vanished, the restart fails exactly where the crash did. The watchdog instead runs `docker compose up -d --force-recreate --no-deps`, which rebuilds the container object and re-evaluates every mount as if fresh. Health comes from `docker inspect` on `.State.Health.Status` for containers that define a healthcheck and `.State.Status` for the ones that don't. It also has a flap guard, a JSON file of heal timestamps per container: two heals per container per six hours, then one "flapping" alert and a stop. Without a give-up threshold the watchdog makes outages worse.

The simplest job is a weekly restart of Docker Desktop itself, in the early hours. Five wedges in three weeks, every one on a VM that had been up for weeks, so uptime now caps at seven days. macOS had a similar problem. The OS shipped with automatic update installs enabled, meaning it could reboot itself into a [FileVault](https://support.apple.com/guide/mac-help/encrypt-your-mac-data-with-filevault-mh11785/mac) unlock screen at 3 a.m. and take the whole lab down until a human typed a password. That setting is off now, FileVault stays on, and the rare unattended reboot is a risk the external watchdogs cover.

The Raspberry Pi covers the case where the Mac goes down completely, which none of the Mac's own watchdogs can report. It pings the Mac on a cron loop and alerts if the whole machine goes silent, and the Mac pings back every five minutes, watching the Pi the same way.

The off-site ARM VM isn't wired in yet. It exists, it's reachable over Tailscale, and a [dead man's switch](https://healthchecks.io/about/) script already runs on the Mac every five minutes waiting for somewhere to ping, but nothing points it anywhere. A full apartment power or ISP outage today takes the Pi's alerting down with it, and nothing off-site would notice. Wiring that switch to the ARM VM is next.

## Backups

The nightly job at 03:00 dumps the Immich database with [`pg_dumpall`](https://www.postgresql.org/docs/current/app-pg-dumpall.html), tars ten named Docker volumes through throwaway [Alpine](https://www.alpinelinux.org/) containers, and snapshots the SQLite databases with [`sqlite3 .backup`](https://www.sqlite.org/backup.html). `pg_dumpall` produces one plain SQL file with everything in the cluster, which a fresh container can restore from directly. The SQLite command uses the database's own backup API, which takes a consistent copy even while writes are happening. Copying a live database file with `cp` gives you a corrupt backup, so the snapshot method matters as much as the schedule. Every artifact gets verified on the spot with `gzip -t` and `tar -tzf`, and the job aborts loudly if free disk drops below its floor.

Secrets and the small databases get encrypted with [age](https://github.com/FiloSottile/age) before they leave the machine. age uses public-key encryption, so the backup job only holds the public key and nothing on the machine can decrypt what it produced. The encrypted files then go to a private git vault with a trick I like: `git checkout --orphan`, one commit, `git push --force`, so the repo carries tonight's backup and no history, and stays small forever. GitHub keeps unreachable objects around for a while after a force push, which would matter for plaintext. Here every object was encrypted before it was committed, so the retention doesn't. Oversized artifacts get slimmed to fit, including the uptime monitor's database, which drops from hundreds of megabytes to a few once the heartbeat history tables are purged. The private age key is stored off the machine, and that's the recovery path if the laptop itself is gone.

The vault and the nightly dump don't cover the 16 TB of photos and documents that make the lab worth protecting in the first place. That's [Backblaze](https://www.backblaze.com/)'s job, and it's the off-site copy in the [3-2-1 backup rule](https://www.backblaze.com/blog/the-3-2-1-backup-strategy/), the one that would matter if the apartment itself were the thing that failed. Its Personal Backup client runs continuously in the background and covers both the internal SSD and the external drive, but it only sees ordinary files. Docker Desktop's VM disk image is opaque to it, so a named Docker volume living inside that image never shows up in a Backblaze scan. That's why the nightly script tars each one out to a plain file first. The Immich database dump is Backblaze's alone to protect. At 772 MB it's too big for the git vault's 90 MB ceiling. Default version history is 30 days, longer than the eight days the corrupted database sat unnoticed but not by a margin I trust, so it's extended to a year for about two dollars a month. Restoring multiple terabytes over residential fiber takes days. Backblaze's mail-in restore option exists for that reason.

Two safeguards make the pipeline trustworthy. The job pushes a heartbeat to the uptime monitor on success, and silence for twenty-six hours raises an alert, so a broken backup gets noticed within a day. A restore-test script also loads the newest dump into a scratch container and asserts the photo count is nonzero, using the same Postgres image as production, because Immich's vector extensions mean a generic Postgres would pass the test and fail the real restore.

## Rebuilding from git

The docker-compose files in the repo are the deployment. `docker compose up -d` per service is the whole mechanism, tracked in git, with no drift between what's written down and what's running. Every service with a database declares a `healthcheck`, and its dependents use `depends_on` with `condition: service_healthy`, so compose waits for Postgres to answer `pg_isready` before Immich starts, with no fixed delays. One script, `bootstrap.sh`, walks a fresh machine through the rest: checks Docker is running and the drive is mounted, places the `.env` files from the decrypted secrets bundle, brings every service up in dependency order, restores each stateful volume from the newest backup tar if it comes up empty, and installs the launchd watchdogs. It's idempotent, so running it twice does nothing the first run didn't already do.

Not everything fits in a compose file. Nginx Proxy Manager, Uptime Kuma, and Home Assistant are GUI-first tools that keep their real configuration in a database or a data directory, and forcing them into full declarative config would mean fighting the tools forever for a small benefit. Home Assistant's config directory is tracked in git directly. NPM and Kuma get their databases dumped and encrypted every night as part of the backup pipeline above. That's restorable, if not declarative, and restorable is what matters if the Mac dies.

There's a runbook for the full rebuild. Clone the repo, fetch the secrets bundle and the age key from where they're kept off the machine, run `bootstrap.sh`, restore the Immich database from the latest dump, and the target is under two hours from a dead machine to a working one. That full drill hasn't happened yet. What has happened, repeatedly, is restoring one service, rebuilding one container, recovering one database in isolation. Each one tested a piece of the plan.

## The kiosk dashboard

An old phone mounted under the monitor runs a kiosk dashboard served by a container, which raises an obvious question: what does the dashboard show when Docker itself dies? A small stats agent runs on the host, outside Docker, a fifty-line Python HTTP server that returns CPU, memory, and disk as JSON. The kiosk page polls the agent and the dashboard container on separate timers, and when two consecutive fetches to the dashboard time out it covers the stale frame with a plain "Docker is down" banner and keeps rendering live numbers from the agent.

## Debloating the Samsung TV and retiring the Xiaomi box

For a long time the living room 65-inch Samsung TV (`UA65TU8000KXXS`, running Tizen 5.5) had a Xiaomi Android TV box (`MiTV-AFKR0`) plugged into HDMI just to run SmartTube, Stremio, Jellyfin, and Moonlight. That meant two remotes on the coffee table and recurring HDMI-CEC bugs. Saying "Hey Google, turn off the TV" in the living room matched two devices at once. The Tuya IR blaster turned the Samsung off, and seven seconds later the Xiaomi box woke up to handle the same voice command and pulled the Samsung right back on over HDMI-CEC.

Getting rid of the Xiaomi box meant running all four apps, a clean full-screen home page, and ad blocking directly on the Samsung TV's Tizen OS, then deleting the Xiaomi box from Home Assistant (`androidtv_remote`, the `Xiaomi Box off -> TV off` automation, and its Lovelace card) and from Google Home. [Stremio](https://www.stremio.com/) has an official Tizen app in the Samsung App Store for 2019 and newer models. Because my setup streams over HTTPS through a debrid service (TorBox), it needs no local torrent engine on the TV. The one hardware limit on 2018 through 2022 Samsung sets is that Samsung dropped DTS audio licensing for those model years, so picking `WEB-DL` streams (`EAC3` or `AAC`) over raw Blu-ray remuxes avoids silent audio. Inside Stremio's settings, turning interface animations off also makes scrolling poster grids noticeably snappier on the TV's 1.5 GB RAM budget.

### What failed before Developer Mode worked

The other apps (`Jellyfin`, `Moonlight`, `TizenBrew` for ad-free YouTube, and a custom full-screen `TV Home` gallery launcher) have to be sideloaded over Samsung's Smart Development Bridge (`sdb`). To unlock Developer Mode on a Samsung TV, you open the `Apps` screen and type `12345`. That sounds trivial until your Samsung Smart Remote has no number keys on it. Three things failed before it opened:

1. Sending `KEY_1`, `KEY_2`, `KEY_3`, `KEY_4`, `KEY_5` over the LAN through Home Assistant's `samsungtv` websocket integration (`remote.send_command`) did nothing. The TV receives network keys fine (sending `KEY_ENTER` at the end clicked into the Video category tile), yet Tizen's `Apps` screen ignores network key events for the `12345` unlock sequence and only accepts input from infrared, the on-screen number pad, SmartThings, or a USB keyboard.
2. Pressing the physical `123` button on the Samsung remote did nothing at first either. While the Xiaomi box was plugged into HDMI, Samsung's Universal Remote (`MBR`) and `Anynet+ (HDMI-CEC)` had bound the remote's auxiliary buttons to the HDMI input, and the remote had dropped its Bluetooth pairing (the power button uses IR, so it kept working while `123` was dead). Deleting the HDMI entry under `Source -> Universal Remote`, turning off `Anynet+ (HDMI-CEC)`, and holding `Return/Back + Play/Pause` together for three seconds re-paired the remote to the TV.
3. Opening the **SmartThings** app on my phone to use its virtual number pad showed the TV as "Offline" even though the TV was on and connected to Wi-Fi. Querying Pi-hole's FTL database (`pihole-FTL sqlite3 /etc/pihole/pihole-FTL.db`) showed why: Pi-hole's default gravity blocklist had blocked `lcprd1.samsungcloudsolution.net` 23,569 times alongside `oempprd.samsungcloudsolution.com`. Those two domains carry the TV's persistent cloud session for SmartThings:

```bash
pihole -w lcprd1.samsungcloudsolution.net oempprd.samsungcloudsolution.com
```

Whitelisting both domains brought the TV back online in SmartThings right away. From there you can open the `Apps` screen on the TV, open the remote in the SmartThings phone app (or press `123` on the physical remote), type `12345`, click `Done`, toggle `Developer mode` to `On`, and enter the host computer's LAN IP.

### The fast-boot standby trap on port 26101

After clicking OK on the Developer Mode dialog and restarting the TV with the remote, the TV's local API on port `8001` (`/api/v2/`) immediately reported `"developerMode": "1"` and the host IP under `"developerIP"`. Connecting to the SDB port (`26101`) still failed with `Connection refused`. Even sending a five-second power hold over the WebSocket (`tv.hold_key('KEY_POWER', 5)`) failed to reboot Tizen, because the initial `Press` command puts the TV into standby and drops the WebSocket before the five-second hold finishes.

Pi-hole's DNS query log exposed what was happening: the TV was firing its XMPP keepalive query to `scs.samsungqbe.com` every 36 seconds without missing a single beat while the screen was black. Pressing power on the remote only puts Tizen into fast-boot standby; the Linux kernel never restarts, and `sdbd` on port `26101` only starts on a cold boot. Turning off the wall socket switch for 15 seconds and turning it back on forced a real cold boot (showing the Samsung Smart TV Knox splash screen) and opened port `26101`.

### Sideloading apps and the host IP to 127.0.0.1 switch

Installing the full Tizen Studio IDE on macOS isn't necessary. The `ghcr.io/georift/install-jellyfin-tizen` Docker image already bundles `sdb`, the `tizen` CLI, and the Samsung distributor signing certificates (`tizen-distributor-signer.p12`). With `Host PC IP` set to the Mac and port `26101` open, one container run pushed [Jellyfin](https://github.com/jeppevinkel/jellyfin-tizen-builds), [Moonlight](https://github.com/OneLiberty/moonlight-chrome-tizen), and [TizenBrew](https://github.com/reisxd/TizenBrew) (`TizenBrewStandalone-Old.wgt` for Tizen 5.5):

```bash
docker run --rm --platform linux/amd64 -v /tmp/tizen-wgt:/wgt \
  --entrypoint bash ghcr.io/georift/install-jellyfin-tizen:latest -c '
    sdb connect <TV_IP>
    tizen install -n /wgt/Jellyfin.wgt -t UA65TU8000KXXS
    tizen install -n /wgt/Moonlight.wgt -t UA65TU8000KXXS
    tizen install -n /wgt/TizenBrewStandalone-Old.wgt -t UA65TU8000KXXS
  '
```

SmartTube is Android-only. Its Tizen counterpart is [TizenTube](https://github.com/reisxd/TizenTube), which runs inside TizenBrew and injects ad blocking, SponsorBlock, and DeArrow into `youtube.com/tv` every time the app opens (fetching the latest `@foxreis/tizentube` module from jsDelivr so ad-block updates arrive automatically). TizenBrew works by running a background Node.js service on the TV (`xvvl3S1bvH.StandaloneService`) that connects to the TV's own SDB port (`127.0.0.1:26101`) to relaunch the app in debug mode. Because Tizen's `sdbd` firewall only accepts connections from the IP saved in Developer Mode, you do a two-step IP switch:

1. Set **Host PC IP** to your computer's LAN IP and cold-boot from the wall socket so your computer can push `.wgt` packages over port `26101`.
2. Once all `.wgt` packages are installed, open `Apps`, enter `12345`, change **Host PC IP** to `127.0.0.1`, and cold-boot from the wall socket once more. From that point on, TizenBrew on the TV can talk to `127.0.0.1:26101` by itself without needing your computer.

### Rebranding TizenBrew as YouTube and remapping the Netflix and Prime buttons

Out of the box, TizenBrew appears on the Samsung home ribbon as `TizenBrewNextGeneration` with a homebrew icon and stops at a module selection menu on launch. Because a `.wgt` file is a standard ZIP archive containing `config.xml`, `icon.png`, and the bundled web/service code, we unpacked `TizenBrewStandalone-Old.wgt`, replaced `icon.png` with a 512x512 YouTube icon, changed `<name>` in `config.xml` to `YouTube`, and set `autoLaunchModule` in `service-nextgen/service/dist/index.js` to `"npm/@foxreis/tizentube"`.

One signing trap showed up when pushing the modified `.wgt` back to the TV: `wascmd` rejected the in-place overwrite with `install failed[118, -11], reason: Author certificate not match` because the upstream release was signed with the original author's certificate while our repackaged build was signed with the container's `/home/developer/author.p12`. Also, `tizen uninstall -p xvvl3S1bvH` fails with `The package is not exist`; Tizen requires the full `<packageId>.<appName>` string (`tizen uninstall -p xvvl3S1bvH.TizenBrewStandalone -t UA65TU8000KXXS`) before installing the re-signed package.

That same background Node.js service (`StandaloneService`) inside `YouTube.wgt` also let us remap the physical `Netflix` and `Prime Video` shortcut buttons on the Samsung remote to open **Stremio** and **YouTube**. Samsung hardcodes those buttons in firmware, and two traps hit us along the way:

1. **Both apps must stay installed on the TV (just removed from the home bar):** I had deleted Netflix and Prime Video earlier, which makes pressing their remote buttons open the Samsung App Store download page instead of launching an app ID. When I tried to reinstall them from the store, the TV threw error `1144001: The server is down`. Checking Pi-hole showed that `sastv.samsungqbe.com` (which stands for **S**amsung **A**pp **S**tore **TV**, `alb-prd-sastv-api...`) had been blocked along with the ad domains. Unblocking `sastv.samsungqbe.com` and `*.api.amazonvideo.com` fixed the store right away.
2. **Checking `d.visible === true` instead of `d.running`:** Once installed, Netflix (`3201907018807`) and Prime Video (`3201910019365`) expose their state on the TV's local REST API at `http://127.0.0.1:8001/api/v2/applications/<id>`. Because Samsung preloads Netflix in the background (`prelaunch.support = true`), `/api/v2/applications/3201907018807` reports `"running": true, "visible": false` even when Netflix is closed. Our first version checked `d.visible || d.running`, which caused the TV to think the Netflix button was being pressed every three seconds and yank Stremio into the foreground on a loop. Checking strictly `d.visible === true` every 400 ms inside `StandaloneService` catches only real button presses, closes Netflix or Prime Video via `DELETE`, and launches Stremio (`IkWsFHtOY9.Stremio`) or YouTube (`xvvl3S1bvH.TizenBrewStandalone`):

```javascript
fetch('http://127.0.0.1:8001/api/v2/applications/3201907018807')
  .then(function (r) { return r.json(); })
  .then(function (d) {
    if (d && d.visible === true && Date.now() - _lastHijack >= 3500) {
      _lastHijack = Date.now();
      tizen.application.launch('IkWsFHtOY9.Stremio');
      fetch('http://127.0.0.1:8001/api/v2/applications/3201907018807', { method: 'DELETE' });
    }
  });
```

### Building a full-screen gallery home page (TV Home)

Unlike Android TV, 2020 Tizen 5.5 TVs only have a pop-up bottom ribbon (`com.samsung.tv.coba.home`) rather than a dedicated full-screen home page. Because any Tizen `.wgt` application with the `http://tizen.org/privilege/application.launch` privilege can launch installed apps via `tizen.application.launch(appId)`, we built and sideloaded a lightweight full-screen home launcher (`TVHome.wgt`, app ID `HomelabTVH.TVHome`).

[![Full-screen TV Home gallery launcher running on the Samsung Tizen TV: Van Gogh's Wheat Field with Cypresses as the backdrop, live weather from Open-Meteo and an editorial clock in the top right, artwork plaque in the lower left, and a five-app dock for Stremio, YouTube, Jellyfin, Moonlight, and Browser across the bottom](</images/posts/homelab/tv-home-museum.png>){: srcset="/images/posts/homelab/tv-home-museum-480.png 480w, /images/posts/homelab/tv-home-museum-960.png 960w, /images/posts/homelab/tv-home-museum.png 1920w" sizes="(max-width: 800px) 92vw, 770px"}](</images/posts/homelab/tv-home-museum.png>)

*The custom `TV Home` `.wgt` launcher running on the Samsung TV, pulling public-domain paintings from The Met and nature photography from Wikimedia Commons alongside live weather.*

It bundles six full-resolution 4K museum paintings (3400px to 4000px master scans of Van Gogh, Monet, Hokusai, Church, and Duncanson from **The Metropolitan Museum of Art** `primaryImage` endpoint and the **Cleveland Museum of Art Open Access API** `images.print.url` endpoint) inside the `.wgt` so it renders with zero network delay on boot, and then pulls additional 3400px+ horizontal landscape masterworks from the Cleveland Museum of Art API (`openaccess-api.clevelandart.org`) and 3840px 4K UHD nature photography from the **Wikimedia Commons Featured Landscapes API** (`iiurlwidth=3840`). Two details matter for image sharpness on a 65-inch 4K TV: declaring `<tizen:metadata key="http://samsung.com/tv/metadata/html5.4k.support" value="true"/>` in `config.xml` so Tizen renders the WebView at native 4K instead of upscaling a 720p buffer, and filtering the museum and Wikimedia API responses strictly for horizontal aspect ratios (`width / height >= 1.25` and `width >= 2800`) so `object-fit: cover` never crops a narrow vertical portrait across a widescreen panel. The top-right corner displays a large editorial clock and live local weather from **Open-Meteo** (`api.open-meteo.com`), while the bottom row holds a five-app dock (**Netflix** with the red `N` logo mapped to launch Stremio `IkWsFHtOY9.Stremio` so anyone in the house knows what to click, **YouTube**, **Jellyfin**, **Moonlight**, and **Browser**) navigated with the Samsung remote's left/right arrows and `OK` button. Pressing `Up` cross-fades to the next 4K museum or nature backdrop, and pressing `Down` hides the dock completely so the 65-inch screen turns into a framed painting.

One packaging quirk showed up when installing `TV Home`: because `config.xml` had `<name>TV Home</name>` with a space, `tizen package` named the output archive `TV Home.wgt`. Passing a filename with a space to `tizen install -n "TV Home.wgt"` transfers the file to `/home/owner/share/tmp/sdk_tools/tmp/` and then fails silently inside `wascmd` because Tizen's on-device installer splits the remote path on whitespace. Renaming the archive to `TVHome.wgt` (no spaces) before running `tizen install` fixed it immediately.

The first launch on the TV also exposed three CSS traps specific to Tizen 5.5, which ships an older Chromium 69 web engine from 2018:
1. **`inset: 0` leaves background layers at 0x0 pixels:** The CSS `inset` shorthand was only added in Chromium 87. Using `position: absolute; inset: 0;` on the wallpaper container gave it zero width and height on the TV, rendering a blank black background while looking fine in desktop Chrome. Using explicit `top: 0; left: 0; right: 0; bottom: 0; width: 100vw; height: 100vh;` with real `<img object-fit="cover">` layers fixed the backdrop.
2. **Flexbox `gap` did not exist in Chromium 69:** Flexbox `gap` landed in Chromium 84, so every `display: flex; gap: 24px;` row collapsed its spacing to zero on the TV. Using `justify-content: space-between` and explicit `margin-right` values restored the layout.
3. **Hardcoding `1920px` by `1080px` overflows the `1280x720` Tizen WebView:** By default, Tizen's web runtime opens in a `1280x720` CSS viewport and scales to 4K at the compositor. Sizing the shell and typography in `vw` and `vh` units (`100vw` by `100vh`) instead of fixed `1920px` pixels makes the layout fit both `1280x720` and `1920x1080` viewports identically.

With `Settings -> General -> Smart Features -> Autorun Last App` enabled on the TV and a Home Assistant automation calling `media_player.play_media` (`media_content_type: app`, `media_content_id: HomelabTVH.TVHome`) whenever the TV state changes to `on`, turning the TV on boots straight into `TV Home`. Because `TV Home` declares `background-support="enable"` in `config.xml`, it also stays alive in memory when another app opens on top of it and runs the same 400 ms `d.visible === true` watcher for the Netflix and Prime Video buttons from the moment the TV turns on.

### Pi-hole blocklist and on-TV speedup checklist

Checking the Samsung TV's historical DNS queries in Pi-hole let us block the ad, automatic content recognition (ACR), Samsung TV Plus EPG, and partner-feed servers without breaking the store or SmartThings:

```bash
# Block Samsung Ads, ACR telemetry, TV Plus EPG, and partner feeds
pihole -b \
  ads.samsung.com \
  config.samsungads.com \
  samsungads.com \
  events.samsungads.com \
  acr0.samsungcloudsolution.com \
  log-config.samsungacr.com \
  samsungacr.com \
  tvpnlogopus.samsungcloud.tv \
  tvpnlinupepgpus.samsungcloud.tv \
  disney-curated-partner-feeds-prod.bamgrid.com \
  config-cd-dmgz.bamgrid.com \
  tvx.adgrx.com

# Keep SmartThings and Samsung App Store working
pihole -w lcprd1.samsungcloudsolution.net oempprd.samsungcloudsolution.com
pihole -b -d sastv.samsungqbe.com
```

On the TV itself, four settings freed up the rest of the memory and CPU:
1. **Disable Samsung TV Plus:** Highlight the Samsung TV Plus icon on the home ribbon, press down, choose `Remove`, and select **Disable** (this kills the background live-streaming daemon instead of merely hiding the icon).
2. **Turn off Smart Hub auto-popups:** Under `Settings -> General -> Smart Features`, turn off `Autorun Smart Hub` and `Autorun Samsung TV Plus`, and leave `Autorun Last App` on.
3. **Disable ACR frame sampling:** Under `Settings -> Support -> Terms & Privacy -> Privacy Choices`, uncheck `Interest-Based Advertisements` and `Viewing Information Services`.
4. **Clear cached app data:** Run `Settings -> Support -> Device Care -> Start Device Care`.

## Day-to-day use

For the people using these services, almost none of the engineering above is visible. Family abroad opens a plain HTTPS link to see new photos. Nobody types a Tailscale key or remembers a port number. The kiosk phone needs no attention to stay current. New tiles and layout changes reach it through a 60-second data refresh, and changes to the dashboard itself propagate to the wrapper within 30 minutes. A second dashboard, [Homepage](https://github.com/gethomepage/homepage), lists links and live container status for every service, so "which port was Stirling PDF on again" stopped being a question I ask myself. Audiobookshelf and Home Assistant both have real mobile apps, and most days nobody opens a browser at all.

A few things sit between fully public and fully private. The kiosk dashboard sits behind an access list in NPM, so it degrades to a login prompt. Nothing that counts as a secret (API tokens, database passwords, the age key) ever gets near a commit. Every `.env` and `.db.env` file is gitignored, and the ones that do leave the machine leave encrypted, in the vault described earlier.

The admin tools never got a public proxy host. The proxy's own panel, the uptime monitor, [Dozzle](https://github.com/amir20/dozzle) for logs, and [FileBrowser](https://github.com/filebrowser/filebrowser) are LAN and Tailscale only, and the Tailscale ACL is what enforces that. I also checked NPM's live config against what I thought was exposed. It's easy to leave a proxy host behind from an earlier draft of a setup, and it's the kind of thing to check once a year.

## What I learned

1. Docker on macOS makes every attacker look like the gateway IP, so the first hop has to live outside Docker. That's the reason for the native nginx and pf setup, and PROXY protocol is how the real address survives the hop into Docker.
2. [HTTP 200 is not health](https://sre.google/sre-book/monitoring-distributed-systems/). Immich answered for eight days while its database was dead. Monitor the process and the query path, and treat a green HTTP check as the weakest signal.
3. `restart: always` restarts the container with the same broken config. Recreating the container re-evaluates mounts and config.
4. A watchdog needs a give-up threshold. Two heals per six hours, then alert and stop, or the watchdog becomes the problem.
5. A backup without a heartbeat fails silently, and a backup you've never restored might not work. Test restores against the production image, because extensions make a generic database pass a test it should fail.
6. Cap uptime when the evidence says so. Five Docker wedges in three weeks got a standing weekly restart, and the wedges stopped.
7. A server that's down can't send its own alert. Every monitor needs one watcher outside its own failure domain, which is why the Raspberry Pi and the Mac watch each other. The off-site VM is meant to be the third watcher for a whole-apartment outage, and that part is still unwired.
8. Smart TVs have enough hooks to replace a streaming box if you audit their DNS and sideload over the developer bridge. Blocking Samsung's ad and ACR domains in Pi-hole while whitelisting `lcprd1.samsungcloudsolution.net` and `sastv.samsungqbe.com` strips the ads without breaking SmartThings or the app store, and a 20-line loop inside TizenBrew's background service can repurpose the hardcoded Netflix and Prime Video remote buttons.
